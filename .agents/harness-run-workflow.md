# Harness run workflow

Applies to feature implementation, review, and explicitly requested harness maintenance or evaluation. Keep the required quality gates; reduce repeated model calls, context, and command reruns. A shorter run is useful only when its acceptance and verification evidence remains complete.

## Establish scope once

1. Record branch, commit, tracked/staged/untracked status, task boundary, fixed requirements, acceptance quantities, prohibitions, Node/pnpm versions, and relevant baseline findings. Preserve user changes. For harness-only maintenance, mark product-domain rows inapplicable and review affected architecture references.
2. Check workspace dependency edges against manifests before editing. A justified dependency inside the allowed boundary permits its generated root lockfile change unless the task prohibits it; keep the lockfile diff to that edge and unavoidable metadata. Obtain a boundary exception for other root configuration. Do not use undeclared imports or flatten architecture to avoid an edge.
3. Check whether the existing install works. Install only when dependencies or lockfile change, a required package is missing, or the install is broken. Use the repository's supply-chain checks. If sandbox network access blocks an install, retry the unchanged command with required permission before changing flags or touching `node_modules`.
4. Consult comparable baseline verification evidence, including audit, Biome, and Knip. If absent, run Knip once before edits and separate actionable findings from configuration hints. Do not alter ignores or root Knip configuration to hide bounded-feature findings.

## Gather context and implement

- Discover paths with targeted `rg --files` and symbol searches. Batch independent searches and bounded source reads in one tool call when possible. Print only needed ranges, paths, counts, and diagnostics; save full logs on disk. Do not dump lockfiles, generated output, whole directories, or whole diffs into model context.
- Load the Cellix skill and triggered references once, then inspect actual applicable source, composition, exports, interfaces, and test companions. Re-read only changed or uncertain parts. Classify every concept by identity and lifecycle before choosing a slice; record why each applicable omission is behaviorally inapplicable.
- Use one compact working record per run at `.agents-work/<run-id>/record.md` if authorized, otherwise an authorized temporary path. Retain the initial snapshot, concept classification, reference-to-destination map, dependency decisions, acceptance evidence, verification results, and usage counters there. Update changed rows rather than generating overlapping plans, tables, or repeatedly restating stable context. Keep raw command output in `.log` files and inspect targeted diagnostics.
- Map required behaviors and errors to the owning layer, application contract, HTTP status/code, focused test, composed host acceptance, and docs where applicable. For each material rule, choose inputs and exact expected results that reject a plausible wrong implementation. Count distinct executed inputs for quantified criteria; A-AC11 needs two separate filter combinations, including `q` + `modality` + `status`, with counterexamples. Test direct application failures and unchanged state, adapter/repository/unit-of-work semantics, and each affected public workflow as required by the Cellix skill and review. Verify rendered API headings, examples, and error tables.
- Implement by owning layer and run the affected focused check after a coherent change. Avoid repeated successful checks and parallel Turbo pipelines that write the same artifacts. Inspect one failure's saved diagnostic before changing code or rerunning a command.

## Verify and finish

1. Complete the Cellix review in the same record. Resolve structural and semantic differences, quantified-evidence shortfalls, and patch-introduced findings. Check the affected test types, owning-layer tests, host acceptance, and rendered docs before the full gate.
2. Run **`pnpm run verify` after the final implementation change**. Save complete output to a log and inspect a short stage summary. If it fails, inspect the failed stage, fix the cause, rerun affected focused checks, then repeat the full gate. Do not repeat an unchanged gate while its same blocker remains. When a prerequisite blocks later stages, execute those stages once as applicable and mark the full gate failed; do not substitute them for a passing full gate. Run security checks under [verification policy](verification-policy.md), even when an earlier stage stops the gate.
3. Compare final Knip findings with baseline. Review `git diff --name-status`, staged diff, and untracked files against the initial snapshot and boundary, including prohibited behavior changes within allowed folders. Run working and staged whitespace checks. Do not stage, commit, push, or bypass hooks without explicit authorization.
4. Report exact fresh versus cached commands, exit status, unexecuted stages, open/ignored/unavailable security findings, acceptance counts, and limitations. Do not infer cost, credits, or vendor approval from token counts.

## Comparable usage evaluations

Use matched task requirements, starting commit, dependency tree, model/settings, tools, permissions, cache policy, and verification policy. Compare complete output and acceptance quality before claiming a speed or token improvement. Capture cumulative usage snapshots at start, after context gathering, implementation, focused review, and final verification; derive phase deltas. Include tool/retry/subagent usage when exposed.

For local Codex session exports, use `node scripts/session-usage.mjs <session.jsonl>` or its `.jsonl.zst` form. The script reads the final cumulative counter and validates it against the sum of per-call counters. Cached input is included in input; reasoning is included in output. Compare every digit with the raw export before transcribing. Iteration 8's published evaluation omitted the leading `9` in input, cached, and total tokens: the actual session totals are 9,739,433 input, 9,585,024 cached input, 37,408 output, and 9,776,841 total. Treat previous comparisons using 776,841 as invalid. Record the export path, phase timestamps, elapsed time, and any interventions; mark unavailable counters explicitly.
