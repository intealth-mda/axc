# Harness run workflow

Applies to feature implementation, review, and explicitly requested harness maintenance or evaluation. Keep the required quality gates; reduce repeated model calls, context, and command reruns. A shorter run is useful only when its acceptance and verification evidence remains complete.

## Establish scope once

1. Record branch, commit, tracked/staged/untracked status, task boundary, fixed requirements, acceptance quantities, prohibitions, Node/pnpm versions, and relevant baseline findings. Preserve user changes. For harness-only maintenance, mark product-domain rows inapplicable and review affected architecture references.
   Select the Node version in `.nvmrc` before running installs or checks, and confirm the pnpm version from `package.json` once. Reuse that environment for the rest of the run.
2. Check workspace dependency edges against manifests before editing. A justified dependency inside the allowed boundary permits its generated root lockfile change unless the task prohibits it; keep the lockfile diff to that edge and unavoidable metadata. Obtain a boundary exception for other root configuration. Do not use undeclared imports or flatten architecture to avoid an edge.
3. Check whether the existing install works. Install only when dependencies or lockfile change, a required package is missing, or the install is broken. Use the repository's supply-chain checks. If sandbox network access blocks an install, retry the unchanged command with required permission before changing flags or touching `node_modules`.
4. Consult comparable baseline Biome and Knip evidence. If absent, run Knip once before edits and separate actionable findings from configuration hints. Do not alter ignores or root Knip configuration to hide bounded-feature findings. Audit and Snyk are user-owned and outside implementation and evaluation runs unless explicitly requested; follow [verification policy](verification-policy.md) if requested.

## Gather context and implement

- Discover paths with targeted `rg --files` and symbol searches. Batch independent searches and bounded source reads in one tool call when possible. Default to at most 4,000 output tokens per call; raise that only for a named source section that cannot be inspected in smaller reads. Show only needed ranges, paths, counts, and diagnostics. Save full logs on disk. If output truncates, narrow the query instead of repeating a directory dump. Do not dump lockfiles, generated output, whole directories, or whole diffs into model context.
- Load the Cellix skill and triggered references once, then inspect actual applicable source, composition, exports, interfaces, and test companions. Re-read only changed or uncertain parts. Classify every concept by identity and lifecycle before choosing a slice; record why each applicable omission is behaviorally inapplicable.
- Use one compact working record per run at `.agents-work/<run-id>/record.md` if authorized, otherwise an authorized temporary path. Retain the initial snapshot, concept classification, reference-to-destination map, dependency decisions, acceptance evidence, verification results, and usage counters there. Update changed rows rather than generating overlapping plans, tables, or repeatedly restating stable context. Keep raw command output in `.log` files and inspect targeted diagnostics.
- Map behaviors and errors once to their owning layer, application contract, HTTP status/code, focused test, running-host acceptance, and docs in the working record. Treat an in-process Hono request as transport evidence, not running-host evidence. For Task Set B, the running-host scenarios must reach course search and each enrollment route, with at least one successful workflow and representative specified error codes. Use the Cellix skill's Behavioral Evidence review for exact expected results, A-AC11's discriminating combinations, direct application validation, persistence semantics, and rendered docs; do not reproduce that checklist in later plans or tool output.
- For each optional list filter, create counterexamples that differ on that filter and assert complete expected IDs or learner keys for a separate request. A combined-filter request is additional evidence; it cannot stand in for each individual filter. Test state and audit fields, not only response counts.
- For custom command persistence, record distinct executed assertions for a complete stored-record ↔ aggregate round trip with nested history, defensive copies on both read and save paths, repository create/get/save, unit-of-work commit and rollback, and concurrent write serialization when that mechanism enforces an invariant. A test filename or a single status/count assertion does not close these rows.
- Implement by owning layer and run the affected focused check after a coherent change. Use package-local typecheck or build checks while a slice is incomplete; defer the workspace-wide typecheck and build to the final gate unless a cross-package failure needs diagnosis. Avoid repeated successful checks and parallel Turbo pipelines that write the same artifacts. Inspect one failure's saved diagnostic before changing code or rerunning a command; record the cause and changed file before the retry.

## Verify and finish

1. Complete the Cellix review in the same record. Check the actual fixtures and assertions against its Behavioral Evidence questions, then resolve structural differences, quantified-evidence shortfalls, and patch-introduced findings. Run each changed feature package's test command directly once after its last relevant change, outside Turbo's task cache; save the logs and test counts. After needed build prerequisites, run `pnpm --filter @axc-verification/archunit-tests test:arch` directly once after its last relevant change; a Turbo cache replay alone is not fresh architecture evidence. Reuse passing evidence only for unchanged code. For Task Set B, require fresh running-host scenarios for search, create, get, list, and status change, plus representative errors; a health-only scenario leaves feature host acceptance open.
2. After the final implementation change for Task Set A/B, run **`node scripts/check-script-policy.mjs && pnpm exec biome check . && pnpm run typecheck && pnpm run build && pnpm run docs:check && pnpm run knip && pnpm run e18e && pnpm run test:arch && pnpm run test`**. Redirect complete output to one log and return only the exit status and bounded stage summary to the model. If it fails, inspect the failed stage's saved diagnostic, fix the cause, rerun affected focused checks, then repeat the full command. Do not repeat an unchanged command while its same blocker remains. When a prerequisite blocks later stages, execute those stages once as applicable and mark the command failed; do not substitute them for a passing run. Report the fresh package and host evidence separately from Turbo cache hits; do not force every build task merely to change a cache count.
3. Compare final Knip findings with baseline. Review `git diff --name-status`, staged diff, and untracked files against the initial snapshot and boundary, including prohibited behavior changes within allowed folders. Run working and staged whitespace checks. Do not stage, commit, push, or bypass hooks without explicit authorization.
4. Report exact fresh versus cached commands, exit status, unexecuted stages, acceptance counts, and limitations. Leave user-owned security checks out of output evaluations unless the user asks to include their results. Do not infer cost, credits, or vendor approval from token counts. Do not score a health-only host scenario as feature acceptance or a cache replay as fresh execution.

## Comparable usage evaluations

Use matched task requirements, starting commit, dependency tree, model/settings, tools, permissions, cache policy, and verification policy. Compare complete output and acceptance quality before claiming a speed or token improvement. When runs differ, report observed ratios without assigning causality to the harness. Capture cumulative usage snapshots at start, after context gathering, implementation, focused review, and final verification; derive phase deltas. Include tool/retry/subagent usage when exposed. Without the scored session export, label phase costs and causes unknown rather than inferring them from aggregate totals.

Keep a small phase budget ledger in the working record: timestamp, cumulative input/cached/output, tool calls and retries when exposed, and the decision that caused a material increase. At each checkpoint, trim repeated context and reruns before continuing; never skip acceptance or verification to meet a token target. At the end, run `node scripts/session-usage.mjs <session.jsonl[.zst]> --timeline` when the export is available and reconcile its output with the ledger. The timeline shows five-minute usage buckets for diagnosis, not task phases or causal attribution. Treat a comparison with different starting commits or cache policies as descriptive, not a harness improvement claim.

For local Codex session exports, read the final cumulative usage counter and reconcile it with per-call totals before transcribing figures. Cached input is included in input; reasoning is included in output. Check every digit against the raw export. Iteration 8's published evaluation omitted the leading `9` in input, cached, and total tokens: the actual session totals are 9,739,433 input, 9,585,024 cached input, 37,408 output, and 9,776,841 total. Treat previous comparisons using 776,841 as invalid. Record the export path, phase timestamps, elapsed time, and any interventions; mark unavailable counters explicitly.
